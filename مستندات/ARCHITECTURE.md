# معمارية تكوين (Takween Architecture)

## نظرة عامة
MVP الحالي مبني كخط أنابيب بسيط:

1. **CLI Layer** (`المصدر/الرئيسية.baa`)
2. **Config Parser** (`المصدر/محلل_النصوص.baa`)
3. **Dependency Resolver** (`المصدر/حل_الاعتماديات.baa`)
4. **Build Planner** (`المصدر/مخطط_البناء.baa`)
5. **Command Executor** (`المصدر/منفذ_الأوامر.baa`)

## المسؤوليات
- `الرئيسية.baa`
  - قراءة الأمر من `معاملات`.
  - مطابقة الأمر العربي/الإنجليزي.
  - توجيه التنفيذ للدالة المناسبة.

- `محلل_النصوص.baa`
  - اكتشاف صيغة 0.1 أو `takween-manifest-v1` دون fallback صامت.
  - التحقق الصارم من الأقسام والمفاتيح والأنواع والقيم.
  - الإبلاغ المبكر عن الأخطاء مع رقم السطر.

- `منفذ_الأوامر.baa`
  - تنفيذ `تهيئة` وإنشاء القالب.
  - تنسيق التحليل والاكتشاف والحل، وتجهيز مجلد المخرج بعد اكتمال الخطة.
  - تشغيل argv المملوكة عبر Process API في Baa.
  - استدعاء parser قبل أوامر البناء/التشغيل.

- `مخطط_البناء.baa`
  - تحويل النموذج ووسائط الاعتماديات المحلولة إلى خطة argv مملوكة وحتمية.
  - إنتاج `takween-build-plan-v1` للفحص الآلي.
  - لا process ولا filesystem ولا network ولا lockfile داخل المخطط.

- `حل_الاعتماديات.baa`
  - حل اعتماديات path/Git/SemVer المتعدية وجمع مصادرها وتضميناتها في خطة Baa.
  - جلب Git وتشغيل checkout بوسائط مهيكلة مع commit مثبت وcache محلي.
  - التحقق من `takween-archive-v1` واستخراجه بأمان إلى cache معنون بـSHA-256.
  - فرض قيود Baa والهدف والقدرات وأسماء الحزم العربية.
  - توليد `takween-lock-v1` مرتب وحتمي وإعادة نموذج المشروع بعد قراءة الحزم.

## حدود المرحلة الحالية
- parser لا يبني AST مستقل؛ يبني نموذج تكوين صارم (Config Model) للاستخدام المباشر.
- build pipeline الأساسي مفعل
  (parse -> validation -> discovery -> resolution -> plan -> execute).
- `check` يمرر عقد `diagnostics-json-v1`، وbuild يستهلك cache وبيان schema 1.
- `run` مفعل (build ثم execute) و`clean` يطبق فحوص أمان قبل الحذف.
- executor لا يستخدم shell؛ build/check/run تمرر argv مباشرة، وinit/clean يستخدمان
  واجهات مجلدات UTF-8 المحمية من Baa. نموذج التنفيذ نفسه معد لـ Windows وLinux.
- executor يحافظ على أكواد `compiler-cli-v1` من Baa (`1` إلى `5`) عبر
  check/build/run/test، ويصنف أخطاء الاستدعاء والعملية المحلية بالأكواد نفسها دون
  تحليل stdout أو stderr. بعد بناء ناجح يبقى كود البرنامج في run/test كود برنامج.
- build يستهلك `target-info-v1` قبل إنشاء خطة المصرّف، ويتحقق من قدرة الربط ويستخدم
  `executable_suffix` المكتشفة بدلا من افتراض `.exe`.
- planner الحالي منفصل عن executor ويمرر جذور `.baa` و`.نظم` معا. الأمر
  `خطة --جسون` يعرض `takween-build-plan-v1` ولا ينفذ المصرّف. اختيار البيان العربي
  `المجمع = "نظم"` يتطلب `target-info-v1.capabilities.nazm_source`، ويسجل
  `مصدر_نظم` في lock، ثم يترك Baa يستدعي الأمر العربي `نظم` عبر argv مباشر.
  عندما لا يحدد البيان مجمعا يثبت المخطط GAS صراحة لحفظ حتمية الخطة.
- v1 التنفيذي الحالي يفهرس عدة أهداف، ويختار build/check/run بالاسم، ويشغل هدف
  اختبار واحدا أو كل أهداف الاختبار، ويحل path/Git/SemVer ويكتب lock، ويدعم
  التحقق دون شبكة والتوريد الحتمي. تبقى globs وبناء المكتبة المستقلة وDAG مساحة
  العمل والسجل العام والنشر لاحقا.

## المعمارية المستهدفة

1. **Manifest Parser** يبني نموذجا typed بلا side effects.
2. **Resolver** يحل path/Git/SemVer المحلي وينتج lock graph حتميا؛ يتوسع لاحقا
   إلى النقل من سجل عام موثوق دون تغيير قواعد الاستخراج.
3. **Planner** يحول النموذج إلى DAG وخطوات Baa موصوفة.
4. **Executor** يشغل argv مباشرة ويجمع stdout/stderr/exit code دون shell، ويحافظ
   على أصل الكود ومرحلة العملية للمراسل.
5. **Reporter** يعرض العربية للبشر وJSON لـ Qalam وCI.
6. **Cache** يستخدم build manifest وhash المحتوى ولا يخمن اعتماديات من النص.

يجب أن تبقى هذه الطبقات قابلة للاختبار مستقلة؛ Qalam يستهلك CLI/JSON ولا يربط
بنموذج parser الداخلي.

## واجهة داخلية (Current Internal API)
- `صحيح تحليل_ملف_تكوين(نص مسار).`
- `صحيح تنفيذ_تهيئة().`
- `صحيح تنفيذ_بناء().`
- `خطة_بناء ابن_خطة_البناء(...).`
- `نص خطة_بناء_إلى_جسون(...).`
- `صحيح تنفيذ_عرض_خطة().`
- `صحيح تنفيذ_فحص().`
- `صحيح تنفيذ_تشغيل().`
- `صحيح تنفيذ_تنظيف().`

## مبادئ التصميم
- Fail-Fast لأي خطأ في ملف الإعداد.
- عقود واضحة للأوامر قبل التوسع في الميزات.
- عزل side effects في executor.
